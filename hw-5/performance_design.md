# Проектирование кеширования и rate limiting

## Вариант 4: Сайт заказа услуг https://profi.ru/ 

## Контекст системы

Profi API реализует модель сайта заказа услуг по типу `profi.ru`.  В системе есть три основные сущности:

- пользователь;
- услуга;
- заказ.

API поддерживает создание пользователя, поиск пользователя по логину и по маске имени/фамилии, создание услуги, получение списка услуг, добавление услуг в заказ и получение заказа пользователя.

Реализация выполнена на `userver-framework/userver`. Основное хранилище данных - PostgreSQL. Redis используется для кеширования и rate limmiting.

## Анализ производительности

### Частые операции

| Операция | Причина высокой частоты |
|---|---|
| `GET /api/v1/services` | Каталог услуг открывается чаще всего |
| `GET /api/v1/orders?userId={userId}` | Пользователь проверяет заказ после выбора услуг |
| `GET /api/v1/users?login={login}` | Точечный поиск пользователя используется повторно |
| `GET /api/v1/users?firstNameMask={mask}&lastNameMask={mask}` | Поиск может часто использоваться оператором |

### Потенциально медленные операции

| Операция | Причина |
|---|---|
| Поиск пользователя по маске | `LIKE/ILIKE` по текстовым полям может сканировать много строк |
| Получение заказа пользователя | Нужно читать заказ и связанные услуги |
| Добавление услуг в заказ | Запись в заказ и позиции заказа |
| Получение списка услуг | Частое чтение одного и того же справочника |

### Ориентиры по нагрузке

Для средне-популярного сервиса приняты такие ориентиры:

- 30 000-50 000 активных пользователей в день;
- 300-700 одновременных пользователей в пиковые часы;
- 5-10 просмотров каталога услуг на одну сессию;
- 1-3 обращения к заказу после выбора услуг.

| Endpoint | Целевое время ответа p95 | Ожидаемая нагрузка |
|---|---:|---:|
| `POST /api/v1/users` | до 250 мс | 20-40 RPS |
| `GET /api/v1/users?login={login}` | до 80 мс из кеша, до 150 мс из БД | 150-300 RPS |
| `GET /api/v1/services` | до 70 мс из кеша, до 180 мс из БД | 500-1000 RPS |
| `POST /api/v1/orders/services` | до 250 мс | 80-150 RPS |
| `GET /api/v1/orders?userId={userId}` | до 100 мс из кеша, до 220 мс из БД | 250-500 RPS |

## Стратегия кеширования

Основная стратегия - Cache-Aside.

Схема работы:

1. API строит ключ Redis.
2. API проверяет Redis.
3. Если ключ найден, ответ возвращается из кеша.
4. Если ключ не найден, API читает PostgreSQL.
5. Полученный JSON сохраняется в Redis с TTL.
6. Ответ возвращается клиенту.

Эта стратегия выбрана потому, что она простая, хорошо подходит для REST API и кеширует только реально  востребованные данные.

### Кешируемые данные

| Данные | Endpoint | Ключ Redis | TTL | Инвалидация |
|---|---|---|---:|---|
| Список услуг | `GET /api/v1/services` | `services:list:v:{version}:limit:{limit}:offset:{offset}` | 10 минут | При создании услуги увеличивается `cache:services:list:version` |
| Пользователь по логину | `GET /api/v1/users?login={login}` | `user:login:{login}` | 10 минут | При создании пользователя удаляется ключ его логина |
| Заказ пользователя | `GET /api/v1/orders?userId={userId}` | `order:user:{userId}` | 60 секунд | При добавлении услуг в заказ удаляется ключ заказа |

Версия списка услуг хранится в ключе:

```text
cache:services:list:version
```

При создании новой услуги версия увеличивается через `INCR`. Старые ключи списка остаются в Redis до истечения TTL, но новые запросы используют уже новую версию ключа.

### Что не кешируется

| Данные | Причина |
|---|---|
| Поиск пользователей по маске | Много комбинаций запросов, низкий ожидаемый hit rate |
| Создание пользователя, услуги, заказа | Записи должны сразу попадать в PostgreSQL |
| Ошибки валидации | Не дают полезной экономии ресурсов |

## Проектирование rate limiting

Rate limiting реализован в Redis. Для публичных endpoints ключ клиента берется из заголовка `X-Forwarded-For`. Если заголовок не передан, используется ключ `local`. Для операции заказа лимит считается по `userId`.

| Endpoint | Алгоритм | Лимит | Причина выбора |
|---|---|---:|---|
| `POST /api/v1/users` | Sliding Window Counter | 10 запросов в минуту | Защита от массовой регистрации без резкого сброса на границе минуты |
| `GET /api/v1/services` | Token Bucket | 300 запросов в минуту, burst 100 | Каталог может открываться серией запросов, короткий burst допустим |
| `POST /api/v1/orders/services` | Sliding Window Counter | 60 запросов в минуту | Защита от повторной отправки формы и лишних записей в заказ |

При превышении лимита API возвращает:

```http
429 Too Many Requests
```

Ответ содержит заголовки:

```http
X-RateLimit-Limit
X-RateLimit-Remaining
X-RateLimit-Reset
Retry-After
```

Формат ошибки:

```json
{
  "error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "Too many requests. Try again later."
  }
}
```

## Влияние на производительность

Кеширование уменьшает число повторных запросов к PostgreSQL. Основной эффект ожидается на каталоге услуг, так как эти данные читаются часто и меняются редко. Для заказа пользователя кеш помогает при повторном открытии заказа, но TTL короче и есть инвалидация после изменения заказа.

Rate limiting защищает API от чрезмерной частоты запросов. Это снижает риск перегрузки PostgreSQL при массовой регистрации, постоянном обновлении каталога или повторной отправке формы добавления услуг в заказ.

## Метрики мониторинга

### HTTP

| Метрика | Назначение |
|---|---|
| RPS по endpoint | Контроль распределения нагрузки |
| p50/p95/p99 latency | Контроль времени ответа |
| Количество `2xx`, `4xx`, `5xx` | Контроль ошибок |
| Количество `429` | Контроль срабатывания rate limiting |

### PostgreSQL

| Метрика | Назначение |
|---|---|
| Количество SQL-запросов в секунду | Проверка снижения нагрузки после кеширования |
| p95 времени SQL-запросов | Поиск медленных операций |
| Активные соединения | Контроль пула подключений |
| Lock wait time | Поиск блокировок при записи |

### Redis

| Метрика | Назначение |
|---|---|
| Cache hits | Успешные чтения из кеша |
| Cache misses | Промахи кеша |
| Hit rate | Эффективность кеширования |
| Used memory | Контроль памяти Redis |
| Evicted keys | Проверка нехватки памяти |
| Redis latency | Контроль задержек Redis |

## Измерение hit rate

Формула:

```text
hit_rate = cache_hits / (cache_hits + cache_misses) * 100%
```

Ожидаемые ориентиры:

| Данные | Хороший hit rate |
|---|---:|
| Список услуг | 80-95% |
| Пользователь по логину | 50-80% |
| Заказ пользователя | 40-70% |

Hit rate нужно считать отдельно по каждому типу кеша. Общий показатель по Redis будет неточным, потому что каталог услуг, пользователи и заказы имеют разный профиль чтения и изменения.

Для ручной проверки ключей Redis:

```powershell
docker compose exec redis redis-cli --scan --pattern "*"
```

Для проверки TTL:

```powershell
docker compose exec redis redis-cli TTL "services:list:v:1:limit:50:offset:0"
```

Минимальная проверка кеширования и rate limiting:

```powershell
.\scripts\check-optimizations.ps1
```
(или `.\scripts\check-optimizations.sh` для bash)
